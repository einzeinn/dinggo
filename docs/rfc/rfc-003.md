---

# ROOT CAUSE ALREADY IDENTIFIED

The current executor contains fallback/guessing behavior.

In particular, `resolve_target_path()` can attempt to infer a target when the planner does not provide a valid target.

The executor can effectively transform:

    read_file + missing/invalid target

into:

    "search the workspace and pick something that looks relevant"

This MUST NOT happen for executable actions.

The executor also treats actions such as:

    general_response
    respond
    info
    general_task
    none

as successful execution paths even though they may produce no actual execution evidence.

This creates a false state where:

    ✓ Completed

can coexist with:

    NO files were read and NO execution evidence was gathered.

That is a contract violation.

---

# NEW CORE PRINCIPLE

Dinggo must follow this architecture:

    LLM decides WHAT needs to happen.

    Application validates WHAT was requested.

    Executor performs EXACTLY that operation.

    Executor NEVER guesses missing information.

    Summary reports ONLY what actually happened.

In other words:

    Planner = intelligent

    Validator = strict

    Executor = deterministic

Do not make the executor "smarter".

Make it more deterministic.

# 1. FIX EXECUTOR TARGET GUESSING

Inspect `core/executor.py`.

Find the logic responsible for resolving targets, especially:

    resolve_target_path()

and any fuzzy filename matching or workspace scanning fallback.

Remove or disable automatic target guessing for executable actions.

If the planner produces:

    action = read_file
    target_path = null

    target_path = ""

    target_path = "-"

Instead return a structured failure.

    "success": false,
    "error": "read_file requires an explicit target_path"
}

The exact implementation should follow Dinggo's existing result schema.

Do not invent a second execution system.

Current behavior can produce:

Inspect `core/planner.py`.

The current planner allows actions such as:

    read_file
    write_file
    list_dir
    edit_file
    run_command
    generate_code
    general_response

and performs normalization/fallback mappings.

Do not remove valid existing functionality unnecessarily.

The model should be corrected rather than the executor guessing what the model meant.
